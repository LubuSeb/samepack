# Real release-archive checks

Tiny fixtures are useful for regression tests, but they are not persuasive
evidence that archive forensics works in the wild. These checks use unmodified
archives generated by GitHub for the ripgrep project.

## Same tag, different formats

Inputs:

- ripgrep 14.1.1 source as TAR.GZ: 581,402 bytes
- ripgrep 14.1.1 source as ZIP: 676,830 bytes
- 269 inspected entries

Samepack compared both archives in 56 ms on the development machine. The raw
SHA-256 hashes differ, but their logical content root is identical:

```text
CONTENT IDENTICAL — raw bytes differ only in packaging metadata or encoding
before    sha256:4dad02a2f9c8c3c8d89434e47337aa654cb0e2aa50e806589132f186bf5c2b66
after     sha256:4e72abebc1b1c5fd7df28805db8d1f647266a9709114b962de921bc49591812a
content   sha256:c0b2909c4653564949ff7d1c599e70ba1b6cb6105355e2eadb74527272023ebd
reason    archive format changed (tar.gz -> zip)
reason    entry modes changed
```

Exit code: `0`.

## Two real versions

Samepack then compared the GitHub source archives for ripgrep 14.1.0 and 14.1.1.
It detected and ignored the versioned wrapper directories, then reported the
payload beneath them:

```text
CONTENT CHANGED — 1 added, 1 removed, 39 modified path(s)
reason    top-level release directories ignored (ripgrep-14.1.0 -> ripgrep-14.1.1)
+ .github/FUNDING.yml
- doc/rg.1.txt.tpl
~ CHANGELOG.md  84121d281466 -> d60f8cf2583a
```

Exit code: `3`.

## A bug this check caught

The first run rejected GitHub's TAR.GZ because it contains a POSIX global PAX
metadata record. That record is packaging metadata, not a release file. Samepack
now handles it explicitly, with a regression test, while still rejecting unknown
special TAR entry types.

The upstream archives were downloaded from GitHub's tag pages for
[14.1.0](https://github.com/BurntSushi/ripgrep/tree/14.1.0) and
[14.1.1](https://github.com/BurntSushi/ripgrep/tree/14.1.1). They are not stored
in this repository.
